Skolenza · Navigation and access

How the side menu, and every permission check, gets its data

One login feeds two separate trees from the backend. One drives the sidebar and the request ids. The other drives route guards and screen gates. They use different keys and different ids, and they must not be mixed.

Read from core/stores/feature-page.store.ts, current-user-permissions.store.ts, layout/app-aside-menu/, core/guards/ and core/interceptors/.

The whole picture

Two lanes, two stores

Both lanes start from the login session. Lane A is the menu tree: it decides what the sidebar shows and which ids go onto API requests. Lane B is the permission matrix: it decides whether a route may open and whether a screen shows its buttons.

Same hierarchy, several names

Module, sub-module, operation

The backend models a tree: groups that contain pages, and pages that carry operations. Each payload names the levels differently, and the host admin screens use a third set of names. This table lines them up by role.

Presence is the grant

Both trees list only granted operations. There is no hasAccess: false row to read. If an operation is in the list, the session may use it.

Operation names are backend data

View, Add, Update, Delete, Verify, Submit and the rest are plain strings. The app has no enum for them, and matching ignores case.

Lane A

How the sidebar is built

my-menu→FeaturePageStore.nodes→scope filter→map to items→sort→search filter→render

  1. Fetch, with a cache in front

    GET /Navigation/my-menu takes no parameters, because the session decides the scope. The tree is stored in localStorage as feature-pages and hydrated when the store starts, so the sidebar paints from cache with no skeleton. The sidebar's ngOnInit calls ensureLoaded(), which revalidates behind the cache on every boot.

  2. Pick the scope

    Role type 0 (Host) reads nodes with moduleScope 2. Admin, StaffMember and Manager read scope 1. The COMMON_MENU subtree is dropped here, because it lives in the header user menu.

  3. Map each node to a menu item

    Routes, icons and optional label overrides come from ASIDE_MENU_MODULE_UI, keyed by moduleCode. The API's own urlPath and iconKey are ignored: the paths do not match the app's routes, and the icon is null on every module.

  4. Sort, search, highlight

    Nodes carry no ordering field, so siblings are sorted by label. Search keeps a node if it or a descendant matches. The active row is the longest menu route that is a segment-prefix of the URL, so staff members stays unlit on staff members/password-management. Ancestors of the active row auto-expand, and expanded ids persist as sidebar-expanded.

The sidebar applies no permission filter of its own

The code says why: my-menu already returns only what the session may see, so a second check could only subtract from what the API granted. A page a role cannot reach is simply not in the tree.

A missing map row hides a granted page

The backend can grant a module the app has no route for. Adding an entry to ASIDE_MENU_UNMAPPED_MODULES records that as a decision. A spec holds the two lists disjoint.

Lane A

Operation checks from the menu tree

After each load the store builds moduleIndex: a map from normalised moduleCode to { moduleId, displayName, operationIds }. Every node is indexed, not only leaves. Because it is derived from nodes(), clearing the store empties it, so one institution's ids cannot leak into the next session.

Soft gates fail open on purpose

Failing open costs a button that answers 403. Failing closed costs a screen nobody can use. A session that receives no tree at all must not lose every screen.

One URL, several possible codes

Callers can pass a list of codes. A host tree publishes INSTITUTION_DEVICES where a institution tree publishes INSTITUTION_DEVICE_SETUP. The session's own tree picks the one it has, preferring a code that publishes the requested operation.

Lane B

How the permission matrix is loaded

CurrentUserPermissionsStore starts by reading loginInfo from storage. That decides host or institution, and whether the user is a super admin. It then loads modules in a fixed order of preference.

SessionSuper admin?Load order
Host hostRoleId === 1. No fetch at all; every check returns true. 1. GET /HostAccess/bootstrap, mapped one to one.
2. If empty or failed: getHostRoleModulePermissions(hostRoleId). A missing role id is recovered from getHostUserById.
3. Neither works: hasLoadFailed, so the next guard can retry.
Institution Role name or role type name equals "super admin". Still loads, but every check returns true. 1. GET /InstitutionUserAccess/bootstrap. The tree main module → sub module → module is flattened, and grants are unioned by moduleId.
2. If empty or failed: forkJoin of get-role-based-permissions and get-all-institution-operations, joined by enrichPermissions() on moduleId + operationId.
3. Neither works: hasLoadFailed.

The catalog is a separate load

Institution sessions also fetch get-all-institution-operations into moduleCatalog, unfiltered by grants. It exists to resolve numeric ids for modules the role was never granted. A host session skips it, since a host has no institution and the call would 403.

A failed load is not a denial

Failure sets hasLoadFailed and drops the cached promise. The next ensureLoaded() retries. Guards show "Could not load your permissions" instead of sending the user to access-denied.

Menu visibility and route access are separate

The sidebar comes from Lane A. A route is protected by the guards above, which use Lane B. Removing a link does not block the URL, and a guard does not hide a link. A screen that needs both must be covered on both lanes.

Lane A, on the wire

How requests get their ModuleId and OperationId

Many endpoints authorise against a module and an operation. moduleOperationInterceptor attaches both, so no call site has to. It runs last in the chain: unavailableRoute, error, auth, loading, moduleOperation. A 401 retry re-sends the original request, so ids are resolved fresh.

  1. Find the route row

    Only URLs under environment.apiUrl count. Lookup order is an exact METHOD /path row, then a wildcard row where {id} matches one segment, then a controller-level fallback. A hand-written row always wins. Matching ignores case.

  2. Skip what must not be stamped

    Denied controllers get nothing: Navigation (so the menu request cannot wait on itself), Auth, ModuleOperation, OperationsMaster, ParentModule, SubModule, PlanModuleMapping, Option, Enum, CommonMenu, ClientInfo, StatData, Image, plus /institution/get-all-institution-operations.

  3. Infer the operation when there is no row

    The fallback reads GET as View, DELETE as Delete, a path ending in create or add as Add, and every other write as Update. Reads and deletes use the query string. Other writes use the body.

  4. Resolve ids from the menu tree

    The row's moduleCode and operation name go to FeaturePageStore.moduleOperationIds(). If the tree is already loaded it dispatches at once. On a cold start with no cache it waits for ensureLoaded(), which never rejects.

  5. Write them where the endpoint binds them

    Three carriers: query as ModuleId and OperationId, body as moduleId and operationId (PascalCase inside FormData), or nested under permissionRequest for /DefaultEmailConfig. A value the call site already set is never overwritten.

Nothing resolved means nothing sent

If neither id resolves, the request goes out bare. An absent id is honest; a zero would be authorised against. In dev mode, a page that resolves without the operation logs a warning that names the code and the operation.

The interceptor does not enforce

It only labels the request. The API decides. An operation missing from the tree means either a wrong route row or a grant the session does not have, and the API answers 403 for the second.

Two id spaces, two methods

FeaturePageStore.moduleOperationIds() takes a moduleCode and returns ids from my-menu. CurrentUserPermissionsStore.identifiersOf() takes a moduleName and returns ids from the institution catalog. The differing method names are what keep them apart. Never pass one's ids where the other's are expected.

Separately, unavailableRouteInterceptor fails a request locally with a 404 and "This feature is not available on the server yet." when the API is known not to serve that controller or route. It runs first, and it is why some built screens show that message.

Where the data comes from

Who defines modules, and who grants them

1. Host defines the catalog

Host screens under /app/modules: Modules (groups), Sub-modules (leaf pages), Operations, and Module-operations (which operations a page offers). PlanModuleMapping maps modules to subscription plans.

2. Institution admin grants roles

Roles, then Permissions. The shared PermissionMatrix loads the catalog (get-all-institution-operations) and the role's flat rows (get-role-based-permissions). The catalog builds the grid. The flat rows pre-tick it.

3. Save writes names and ids

POST /UserModuleRolePermission/assign-role-permissions takes one row per cell: moduleId, moduleName, operationId, operationName, hasAccess.

Per-staffMember grants are not served yet

POST /usermodulerolepermission/assign-staffMember-permissions and GET /role/get-permissions are on the unavailable-routes list. The staffMember permission screen exists, but the backend does not answer those calls.

Matrix rules: match the catalog to the flat rows by moduleId plus operationId, never by name. isEnabled in the catalog means "this operation exists", not "ticked". Only the flat rows say what is ticked.

In time order

Session lifecycle

  1. Login succeeds

    #startSession stores loginInfo and the tokens, then calls permissionsStore.loadFromStorage() to start Lane B. It then calls featurePageStore.clear() and featurePageStore.load() to start Lane A. The clear matters: a failed load keeps whatever is in nodes, so a new account on a shared browser could otherwise see the previous account's menu.

  2. Redirect to the dashboard

    The sidebar is already warming while the dashboard chunk loads. Its ngOnInit sets the auth role type from loginInfo and calls ensureLoaded(), which joins the in-flight request rather than sending a second.

  3. Navigating

    Guards call ensureLoaded() on the permission store and wait, so a decision never races an unfinished load. Screens read gates from whichever store their check belongs to.

  4. Cold start of an existing session

    Both stores start themselves. The permission store reloads from loginInfo. The menu store hydrates from the cache, so the sidebar paints at once, and the sidebar then revalidates it. A grant made since the last boot appears without waiting for any expiry.

  5. Logout

    The header clears both stores. The menu store also removes its localStorage cache.

Before you change anything here

Gotchas

  • Add a screen to the sidebar by adding its moduleCode to ASIDE_MENU_MODULE_UI with a route and a PrimeIcons class. Without that row a granted page never appears.
  • Gate a button with FeaturePageStore.canPerformOrUnknown(moduleCode, 'Operation'). Gate a route with a guard from Lane B. Do not use one lane's key in the other's method.
  • Not every module name is verified. permission-modules.ts says only Staff Members, Departments and Designations are confirmed against a live catalog. A wrong name resolves no id, the param is dropped, and the endpoint answers 403.
  • The menu tree is a snapshot of one user's authorisation. It is cached but revalidated on every boot, and it is cleared on both login and logout.
  • Documentation drift: .claude/docs/architecture.md says menu items soft-gate through canAccessOrUnknown. The current sidebar code applies no client filter and trusts my-menu.
  • Codes get renamed. Old and new codes are both mapped where a rename happened (DEPARTMENT and INSTITUTION_DEPARTMENTS, for one), because an old-shape payload may still arrive.
