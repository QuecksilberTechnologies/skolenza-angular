How a policy moves from draft to a rule that applies to an staffMember

A institution policy is versioned, goes through approval stages, is published, and is then targeted at staff members by applicability rules, assignments and exceptions. This page follows one policy end to end, then breaks out each part.

Start to finish

One policy, in the order things happen

Steps 1 to 3 happen once per institution. Every step after that needs the output of the one before it.

  1. Load the seed lists

    Institution admin
    GET /lookups

    One call returns four backend-owned, read-only lists: categories, statuses, ruleTypes, documentTypes. Nothing here is editable in the app.

  2. Create a policy type

    Institution admin
    POST /types

    Needs a categoryId from step 1. Screen: /institution-policies/types.

  3. Define approval stages

    Institution admin
    POST /approval-stages

    Each stage has stageOrder, approverRoleId, minimumApprovals and isMandatory. A stage with policyCategoryId: null is global. A stage with a category applies only to that category's policies.

  4. Create the policy

    AuthorDraft
    POST /InstitutionPolicy

    One call creates the policy, its first version, its rules and its applicability rows. There are no separate rule or applicability endpoints. A changeSummary is required and is what the audit trail records.

  5. Edit while it is still editable

    AuthorDraftRejected
    PUT /InstitutionPolicy/{id}

    Only these two statuses can be edited. Any other status hides the Edit action.

  6. Submit for review

    AuthorUnder Review
    POST /versions/{versionId}/transition SUBMIT

    Approval stages apply from here until publish.

  7. Approve or reject

    ApproverApprovedRejected
    GET /versions/{versionId}/approval-progress POST …/transition APPROVE REJECT

    Progress shows approvalCount against minimumApprovals for each stage, plus isComplete.

    Rejected goes back to step 5. Edit, then submit again.

  8. Publish

    PublisherPublished
    POST …/transition PUBLISH

    The version is now immutable and can be targeted at staff members.

  9. Target and collect

    AdminStaffMember
    /assignments /exceptions /acknowledgements /documents

    Done in the version workspace: assign staff members, record per-staffMember exceptions, attach documents, and let staff members acknowledge.

  10. Ask who it applies to

    Anyone with module access
    GET /resolve?staffMemberId&effectiveDate

    Returns the published versions that apply to that staffMember on that date, with the reason each one matched.

  11. Retire or change it

    PublisherArchived
    ARCHIVE POST /{policyId}/versions/clone

    Archive a published version to retire it. To change a published version, clone it into a new Draft.

    Clone returns to step 5 with a new version.

Phase 2

What one save creates

POST /InstitutionPolicy
└─ Policy
   └─ PolicyVersion v1            status: Draft
      ├─ PolicyRule[]             policyRuleTypeId, ruleName, ruleConfiguration
      └─ PolicyApplicability[]    who the version targets
changeSummary                     required on every write, recorded in the audit trail

Rules

ruleConfiguration must be a JSON object string, for example {"days":12}. Arrays and bare values are rejected by the backend. The zod schema enforces the same rule in the form.

Applicability

applicabilityMode: 1 is Include, 2 is Exclude. priority breaks ties between matching rows. effectiveFrom is required, effectiveTo is optional.

Targeting fieldSource in the formEditable

institutionLocationId, staffEmploymentTypeId, departmentId, designationId, genderIdLookup store and option APIsYes

minimumServiceDaysWhole-number input, minimum 0Yes
workArrangementType, employmentStatusNo value legend exists, so no select can be builtNo. Existing values are carried through unchanged on save.

Phase 3

Version lifecycle

One endpoint drives every change of status: POST /versions/{versionId}/transition with an action.

ActionLegal fromResultPermission
SUBMITDraft RejectedUnder ReviewINSTITUTION_POLICY_DEFINITIONS · Submit
APPROVEUnder ReviewApprovedINSTITUTION_POLICY_APPROVALS · Approve
REJECTUnder ReviewRejectedINSTITUTION_POLICY_APPROVALS · Reject
PUBLISHApprovedPublishedINSTITUTION_POLICY_APPROVALS · Publish
ARCHIVEPublishedArchivedINSTITUTION_POLICY_APPROVALS · Archive

What the row menu shows

On the policy list, a row action appears only when the status allows it and the user holds that permission. "Open workspace" is always there and is ungated.

Operation names are capitalised

The permission lookup uses Submit, Approve, Publish, Archive, not the uppercase action value. See INSTITUTION_POLICY_LIFECYCLE_OPERATION_NAME.

Phase 4

StaffMember side

All four live in the version workspace at /institution-policies/:policyId/versions/:versionId. It is opened from a row action, not from the menu.

EntityWriteReadNotes
AssignmentPOST /assignments
DELETE /assignments/{id}		GET /versions/{id}/assignmentsTakes staffMemberIds[]. Repeating an staffMember counts as existing, not inserted.
ExceptionPOST /exceptions
POST /exceptions/{id}/decision		GET /versions/{id}/exceptionsPer-staffMember override. overrideConfiguration is a JSON object string, like ruleConfiguration. It is created, then approved or rejected.

Each tab in the workspace reads through its own permission leaf, and the audit trail (GET /{policyId}/audit) has its own leaf as well. It covers every version of the policy and records each write's changeSummary.

The question the engine exists to answer

Resolution

GET /resolve?staffMemberId&effectiveDate returns the published versions that apply to one staffMember on one date. Every result carries a resolutionSource naming why it matched.

resolutionSourceWhy the version applies
APPLICABILITYAn applicability row on the version matched the staffMember.
ASSIGNMENTThe version was explicitly assigned to the staffMember.
EXCEPTIONAn approved per-staffMember exception brought it in.

Read-only, and gated only by module access. A read-only session may still ask. Screen: the "Resolve" button on the policy list.

Two rules

Import writes need the Import operation, reads need View. Assignment import requires the target version to already be Published.

Who can press what

Permissions

The routes have only a coarse role gate (adminManager). There is no hasModulePermissionGuard here. Each button gates itself through FeaturePageStore.canPerformOrUnknown(moduleCode, operation).

The split that surprises people

Submit sits on DEFINITIONS, because the author pushes their own draft out. Approve, Reject, Publish and Archive sit on APPROVALS.

Ids are not stamped for you

InstitutionPolicy is not in MODULE_OPERATION_ROUTES, so no interceptor adds moduleId and operationId. Every call site resolves both from the authenticated menu and passes them itself.
