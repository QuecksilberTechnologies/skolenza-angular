# Professional and academic structure: server-side pagination

## Environment and scope

- Date: 2026-10-19
- Environment: local Angular workspace
- Branch: `development`
- Scope: `core/services/staff-professional-structure-api.ts`,
  `core/services/staff-academic-structure-api.ts`, the two structure pages
  (`features/staff-members/staff-professional-structure/`,
  `features/staff-members/staff-academic-structure/`) and every picker that reads their lists

## Problem

The updated Swagger (`/swagger/v1/swagger.json`, read 2026-10-19) adds `PageNumber` / `PageSize`
to these GETs under `/api/Staff`:

- `professional-structure/masters/{masterType}` (JobFamily, Capability, DutyDefinition)
- `professional-structure/categories`
- `professional-structure/positions`
- `academic-structure/masters/{masterType}` (Session, Programme, Group, Section, Subject,
  CourseOffering)

The `curriculum-delivery` GETs in the same list were already paged (see
[curriculum delivery pagination](../curriculum-delivery-pagination/2026-10-18.md)); the client
already matched them, including `units/{unitId}/topics`. Paths keep the `/api/Staff` prefix, and
`{masterType}` stays the numeric enum. The client sent no paging params, so with the server default
of 10 rows every list and picker would be cut to 10.

Swagger does not publish response schemas. The client assumes the same envelope as curriculum
delivery (`pageNumber`, `pageSize`, `totalRecords`, `totalPages` beside `data`). A response without
paging fields is read as one page, so the change also works against a backend that still returns
the whole list.

## Decision

- `getMasters`, `getCategories` and `getPositions` take a `PageRequest` and return
  `PagedDataResponse<T>`. Other endpoints are unchanged.
- The structure pages are plain `<article>` listings, so each tab uses `pagedList()` with
  "Load more" (`app-load-more`). This follows the pagination UI rule from 2026-10-18. A tab switch
  clears and reloads page 1. A save or status change calls `refresh()`, which keeps the loaded pages.
- The status filter: superseded by the code review fixes below.
- Pickers and lookups need every row, so they use `allPages()`: the reference lists for the
  professional dialogs, the academic dialog pickers, the staff member manage dialog, the staff
  filter and store, bulk-import fields, the policy definition form, curriculum delivery and staff
  operations.
- A category save or status change now also reloads the reference lists, because the category
  tab no longer shares its rows with the position dialog's category picker.

## Code review fixes (all ten findings, user decision)

| # | Finding | Fix |
| --- | --- | --- |
| 1, 2 | `allPages` / `pagedList` read `isSucceeded: false` as an empty page, so callers lost their error toast and tabs showed "No X yet" | Both helpers now fail such a page with its `message` (or a generic one). Lists show Retry, and pickers reach their error handlers. Bulk-import pickers stay empty on failure (`catchError`), so `rxResource.value()` never throws |
| 3 | "Inactive" filtered only the loaded pages | "Active" is sent as `activeOnly=true` and filtered by the server; entering or leaving it reloads the tab. "Inactive" stays client-side (no API option); while pages remain, the empty state says "No inactive X on the loaded pages" / "Load more to check the rest, or change the status filter." An empty "Active" answer offers "Show all statuses", not "Add" |
| 4 | Overlapping reference loads could overwrite newer picker data | One `forkJoin` per load; a new load cancels the one in flight |
| 5 | Returning to Categories or Positions showed stale rows | Every tab switch clears the selected tab's list before reloading it |
| 6 | Staff Operations kept paging after leaving and had no error handler | One `forkJoin` with `takeUntilDestroyed` and an error toast |
| 7 | A failed first page showed both "No X yet / Add" and Retry | The empty state is hidden while the list has failed |
| 8 | One outage raised up to five toasts | Reference lists fail as one batch: one toast, plus the tab's own |
| 9 | Paging params built in three API services | `BaseService.makePageParams()`; named operations for log lines |
| 10 | Duplicated cast-and-toast lambdas; non-`Error` throws showed a blank toast | `shared/utilities/error-message.ts` with a generic fallback |
