# Curriculum delivery: server-side pagination

## Environment and scope

- Date: 2026-10-18
- Environment: local Angular workspace
- Branch: `development`
- Scope: `core/services/staff-curriculum-delivery-api.ts`,
  `features/staff-members/staff-curriculum-delivery/` (component, template, spec),
  `shared/utilities/paged-list.ts` and its spec, `PageRequest` / `PagedDataResponse<T>` in
  `shared/interfaces/staff-members/staff-professional-structure.ts`, and the topics GET in
  `core/interceptors/module-operation-routes.ts`

## Problem

The backend added paging to six GETs under `/api/Staff/curriculum-delivery`: `frameworks`,
`frameworks/{frameworkId}/units`, `units/{unitId}/topics` (new, topics page on their own),
`lesson-plans`, `lesson-deliveries` and `syllabus-progress`. They take `PageNumber` / `PageSize`
(default 1 / 10) and return `pageNumber`, `pageSize`, `totalRecords`, `totalPages`.
`workflow-statuses` and `teaching-assignments` stay unpaged. The page sent no paging params, so
every tab silently showed only the first 10 rows, and the framework picker offered only 10.

## Decision

- Pagination UI rule (user decision): a feature page with a `p-table` uses a lazy table with
  server-side paging; a plain listing without `p-table` uses a server-side "Load more" button.
- Every Curriculum tab is a plain `<article>` listing, so each tab gets "Load more" (page size
  10). `pagedList()` owns the rows, the page counter, the busy flag and cancellation: a new
  request cancels the one in flight, and switching framework clears units and topics.
- Units & Topics: each unit fetches its first page of topics from `units/{unitId}/topics`, with
  its own "Load more topics" button (labelled with the unit name for screen readers).
- Pickers and lookups need every row, so they use `allPages()` (page size 100, page by page until
  `totalPages`): the framework picker, the units given to the topic and lesson plan dialogs, the
  plans given to the lesson delivery dialog, and the plan titles on Delivery Logs.
- The Lesson Plans tab no longer fetches units up front; the lesson plan dialog fetches them when
  it opens, matching the academic-structure "fetch only the selected tab" decision.
- A save, review or delete reloads page 1 of the affected list.
- A response without paging fields is treated as one page, so the page still works against a
  backend without the change.
- The topics GET was missing from `MODULE_OPERATION_ROUTES`; it now carries the same Staff
  Directory `View` stamp as the units GET.

## Live API check (browser, `localhost:4200` against the configured API)

- Confirmed: paging fields sit at the top level of the envelope beside `data`. Framework 1 has
  222 units; `PageSize=100` is honoured (3 pages).
- Found: the units response no longer carries `topics`, so the lesson plan dialog's topic picker
  was always empty. Fixed: `CurriculumUnit.topics` removed; the dialog fetches topics (all pages)
  only for the units of the chosen assignment's course offering (3 requests for Grade 5
  Mathematics, 9 topics). Edits to other fields do not refetch. Save waits until the topics
  arrive, because saving drops picked topics that are not on offer.
- Not verified: whether `lesson-plans` still embeds `topics` (no lesson plans exist yet). The
  lesson delivery dialog's coverage rows read them.
- Observed backend latency: about 1 to 1.9 s per request, and one units page took 18.7 s. Opening
  the lesson plan dialog waits for every units page (sequential).

## Units & Topics: CDK virtual scroll with infinite scroll (user decision)

- Units & Topics only renders through `cdk-virtual-scroll-viewport` with fixed 56 px rows. Units
  and topics are flattened into rows (`unitRows`); the DOM holds about 26 rows whatever the list
  length (91 rows after three pages in the live check).
- Infinite scroll replaces the Load more buttons on this tab: a `more` row (`role="status"`,
  "Loading more units..." / "Loading more topics in <unit>...") stands where a list has another
  page, and rendering it loads that page. The other tabs keep "Load more".
- The units `more` row is held back until the loaded units' topics arrive. Without that, a fresh
  page is one row per unit, the next `more` row is in view at once, and pages cascade (seen live:
  50 topic requests and about 70 units within seconds). After the fix one scroll loads one page.
- Viewport height `calc(100dvh - 16.5rem)` (min 20 rem) so the page itself does not scroll as
  well. Checked at a 1872 px wide window only; the resize to phone width did not take effect.

## Code review fixes (all nine findings)

| # | Finding | Fix |
| --- | --- | --- |
| 1 | A failed page made the infinite-scroll effect call `loadMore()` in a loop | `loadMore()` does nothing after a failure; `loadRendered` skips failed lists; the `more` row shows "Couldn't load more units." with Retry |
| 2 | `pagedList` had no error handler; a failure looked like an empty list | `pagedList` keeps the rows, exposes `error`/`failed`/`retry()`, calls `onError` (toast); each tab shows a Retry line instead of the empty message |
| 3 | A failed topics fetch let Save drop the picked topics | Save is blocked while the topics are in error; it toasts and fetches them again |
| 4 | `loadMore()` could cut short a reload in flight | `loadMore()` does nothing while any request is in flight |
| 5 | Any unit or topic save reloaded page 1 and every unit's topics | Saves and reviews call `refresh()`: every loaded page again in one request (`PageSize = pages x 10`), so the list keeps its length and scroll. A topic save or delete refreshes only the units it left and joined (the unit dialog now closes with `{ unitId }`; `openManageDialog` passes the close value to `onSaved`). A units refresh fetches topics only for new units |
| 6 | The lesson plan dialog sent one topics request per unit at once | At most 4 in flight (`mergeMap`), cached per unit for the dialog's life |
| 7 | The rows effect paired new rows with the old rendered range | Now an `afterRenderEffect`, so it reads the range after the viewport has rendered |
| 8 | Delivery and topic dialogs refetched what the page held | The delivery dialog uses the Delivery Logs plan list; dialog units are cached per framework until a unit save or delete |
| 9 | `unitRows` created lists inside `computed`; the map was never pruned | Topic lists are created where units arrive (`#syncTopics`); a full units refresh drops the lists of units no longer present |

## Second code review fixes

| # | Finding | Fix |
| --- | --- | --- |
| 1 | `refresh()` asked for `pages x 10` rows in one request, past the API's 100-row cap | Requests of at most `MAX_PAGE_SIZE` (100) rows; the last is trimmed so the list keeps its length |
| 2 | A unit whose first topics page failed (or a failed refresh on the last page) had no Retry | The `more` row also stands for a failed list, so its Retry is always reachable |
| 3 | Each units page fired one topics request per unit at once | `requestLimiter(4)` (`shared/utilities/request-limiter.ts`) holds the rest until a slot frees |
| 4 | One topics outage raised a toast per unit | One toast per batch of units |
| 5 | Overlapping framework-list loads could reset units again; a failure was silent | A newer load cancels the older one; a failure shows a toast |
| 7 | Virtual list a11y: viewport not focusable, `aria-label` without a role, a status region per `more` row, topics lost their unit | Viewport is `role="region"`, labelled and `tabindex="0"`; one `sr-only` status region outside it (`unitsStatus`); each topic row carries its unit name for screen readers |
| 8 | `unitRows` read a plain `Map` | Topic lists live in a signal holding a new `Map` on every change |
| 9 | Failed / Retry / Load more markup copied five times | `app-load-more` (`shared/components/load-more`) |
